---\nStatus: Proposed\nImplementation: 0%\nConfidence: High\n---\n# ADR-002: ADR Framework & Decision Process\n\n## Status\nProposed\n\n## Date\n2026-06-04\n\n## Context\nAs Phoenix scales, architectural decisions are being made across multiple layers and subprojects. Without a formal decision framework, the rationale for these decisions is lost, making long-term maintenance difficult.\n\n## Decision\nWe adopt a formal ADR (Architecture Decision Record) framework:\n\n1. **Standard Template**: Every ADR must use the standardized markdown template (Status, Context, Decision, Consequences, Alternatives).\n2. **Canonical Index**: `docs/adr/ADR_INDEX.md` is the authoritative list of all decisions.\n3. **Traceability**: Decisions must reference `docs/MASTER_INVARIANTS.md` to ensure alignment with core laws.\n4. **Lifecycle Management**: Status transitions (Proposed -> Accepted -> Superseded) must be tracked.\n\n## Consequences\n\n### Easier\n- Understanding the "Why" behind the architecture.\n- Onboarding new contributors and AI agents.\n- Tracking the evolution of system constraints.\n\n### More Difficult\n- Requires discipline to document decisions before implementation.\n- Adds overhead to the PR process for architectural changes.\n\n## Alternatives Considered\n1. Inline code comments — rejected as insufficient for cross-cutting decisions.\n2. Wiki/External Docs — rejected to keep documentation co-located with code.\n3. Informal RFCs — rejected as too ephemeral for a 10-year system.\n\n## References\n- [ADR_INDEX.md](./ADR_INDEX.md)\n- [REPOSITORY_CONSTITUTION.md](../governance/REPOSITORY_CONSTITUTION.md)\n
