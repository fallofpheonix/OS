---\nStatus: Draft\nImplementation: 0%\nConfidence: High\n---\n# SPEC-006: Intent State & Actuation Cycle\n\n> This specification defines the format for Intent objects and their transition into authorized events.\n\n## 1. Intent Schema\n\n```text\nIntent {\n    IntentID: UUID\n    Source: IdentityID (e.g., PhoenixMind)\n    Action: ActionType (e.g., RESTART_SERVICE, EMIT_LOG)\n    Parameters: Map<string, Value>\n    CapabilityToken: SHA256 (Token authorizing this action)\n    ReasonPath: string (Human-readable rationale)\n}\n```\n\n## 2. Actuation Cycle\n\n1. **Generation**: Cognition layer emits `Intent`.\n2. **Validation**: Warden checks `CapabilityToken` and parameters against `ActivePolicies`.\n3. **Authorization**: If valid, the Warden signs the intent, transforming it into an `AuthorizedIntent`.\n4. **Execution**: The Runtime executes the `AuthorizedIntent`, which generates an `Event` to be ledgered.\n\n## 3. Reversibility Requirements\n\n- Every Intent of type `MUTATE_STATE` must have a corresponding `INVERSE_ACTION` defined to allow for Path Alpha (Rollback) recovery.\n\n--- \n*Refer to [docs/failure/ROLLBACK_MODEL.md](../failure/ROLLBACK_MODEL.md) for inverse action implementation.* \n
