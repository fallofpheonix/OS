---\nStatus: Draft\nImplementation: 0%\nConfidence: High\n---\n# P-Script Language Semantics\n\n> This document defines the formal semantics of P-Script, the domain-specific language for Phoenix orchestration and logic.\n\n## 1. Core Principles\n\n- **Strict Determinism:** All P-Script execution must yield the same result across all nodes.\n- **Resource Accounting (Gas):** Every operation has a computational cost to prevent infinite loops and resource exhaustion.\n- **Ownership & Isolation:** Scripts operate within strict capability-based sandboxes.\n\n## 2. Type System & Ownership\n\n### 2.1 Value Types\n- `Bool`, `Int64`, `Float64` (fixed-point at runtime), `String`, `Bytes`.\n\n### 2.2 Reference Types\n- `Capability`: A token representing authority to perform an action.\n- `Entity`: A handle to a world or system entity.\n\n### 2.3 Ownership & Borrowing Rules\n- **Move Semantic**: Reference types (`Capability`, `Entity`) are moved by default. Passing them to a function transfers ownership.\n- **Immutable Borrows**: Functions can accept `&T` to borrow a reference. Multiple immutable borrows are permitted simultaneously.\n- **Mutable Borrows**: Functions can accept `&mut T` for exclusive access. Only one mutable borrow can exist at a time.\n- **No Aliasing**: The VM prevents multiple mutable aliases to the same state region to ensure deterministic results.\n\n## 3. Execution & Concurrency\n\n### 3.1 Synchronous Core\n- P-Script execution is strictly single-threaded and synchronous within a single event context.\n- **No Async/Await**: Asynchrony is handled at the Event layer, not within the script logic.\n\n### 3.2 Concurrency Isolation\n- Scripts processing different events may run in parallel but must operate on isolated memory partitions (Temporal Isolation).\n- **Conflict Resolution**: If two scripts attempt to mutate the same long-term state, the Ledger's ordering determines the winner; the second script's Intents are invalidated and must be re-processed.\n\n## 3.3 Side Effects (Intents)\n- P-Script CANNOT perform direct side effects (e.g., IO, mutation of global state).\n- It MUST output `Intent` objects which are subsequently validated and executed by the Warden.\n\n## 4. Error & Exception Model\n- **Fail-Fast**: Any unhandled error (OOM, Gas Exhaustion, Bounds Breach) results in immediate script termination and Intent revocation.\n- **No Global Try/Catch**: Exceptions must be handled locally or propagate as a script failure.\n\n## 5. Determinism Constraints\n\n- **No Floating Point:** Runtime execution uses fixed-point math to avoid IEEE 754 non-determinism.\n- **No Wall-Clock Time:** `now()` returns the current Ledger tick, not system time.\n- **No Randomness:** `random()` is a PRNG seeded by the event's deterministic context.\n\n--- \n*Refer to [docs/architecture/MASTER_BRAIN.md](../phoenixmind/MASTER_BRAIN.md) for P-Script VM integration.* \n
