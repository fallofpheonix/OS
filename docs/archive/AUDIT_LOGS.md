## Phase 0: Resolution of Contradictions

### Contradiction 1: PhoenixMind Utility
**Risk:** PhoenixMind becomes a passive advisor.
**Resolution:** PhoenixMind acts as a **Probability Oracle** capable of traversing the Causal Graph infinitely faster than the human player. While the player can override it, ignoring PhoenixMind frequently costs exponential amounts of Verification Credits (Time/Energy). Disagreement incentives exist when PhoenixMind suffers from "Cognitive Bias" (drift in its own weights), requiring the player to act on human intuition against the machine's corrupted logic.

### Contradiction 2: Trust Farming
**Risk:** Infinite trust farming.
**Resolution:** Implementation of **Trust Provenance**. Trust is not fungible like currency; it is a directed, weighted edge in a graph (A trusts B regarding Context C). Trust decays naturally, and synergistic farming (A trusts B, B trusts A in a loop) is penalized heavily by the `AuditEngine`'s Sybil-detection algorithms.

### Contradiction 3: Ledger Semantics
**Risk:** Does the ledger store Truth or Observed Events?
**Resolution:** The Ledger strictly stores **Observed Events (Claims)**. It is an immutable append-only log of *what was said to happen*, *who said it*, and *what action was taken*. It does **not** store Ground Truth. Ground Truth is the underlying state of the Simulation Engine, which is hidden from all entities (including the player and PhoenixMind).

### Contradiction 4: The Epistemological Stack
**Resolution:**
- **Truth (Ground Truth):** The hidden, objective state of the simulation.
- **Evidence (Telemetry/Data):** Artifacts generated by the simulation, captured by sensors. Can be corrupted or faked.
- **Belief (Hypothesis):** A subjective interpretation of Evidence held by an Entity.
- **Knowledge (Verified Belief):** A Belief that has survived the `CourtEngine`'s Counterfactual Simulation and is recorded in the Ledger as legally actionable.
- **Doctrine (Law):** Knowledge enforced by the Warden/Institutions, imposing penalties for deviation.

**Risk:** "Mathematical Certainty" cannot exist if "Truth" is inaccessible.

**Risk:** "Verified Belief" is ambiguous. Who verifies it?
**Resolution:** **Institutions** (specifically, the Court or Scientific Guilds) create Knowledge. A Belief becomes Knowledge only when it survives adversarial Counterfactual Simulation on the Ledger and is formally accepted by the Consensus Protocol.

**Risk:** False Knowledge -> Doctrine -> Tyranny.
**Resolution:** Doctrine is revoked via **Appellate Replay (Schism)**. If rising Entropy proves a Doctrine is failing, an Entity (or the Warden) can spend massive Verification Credits to run a full historical replay simulating the counterfactual. If the simulation proves the Doctrine caused the Entropy, the Doctrine is revoked, and the Institution that enforced it suffers massive Trust Decay.

### Contradiction 8: Smallest Institution
**Risk:** Can a single person create an institution?
**Resolution:** **Yes.** 1 Entity can form an Institution (e.g., a Lone Archivist, a Dictator, an Oracle). The definition of an Institution is not headcount, but the existence of a **Ledger Contract** binding resources and trust to a specific Doctrine or Knowledge set.

## Phase 3.5: CLI Refactor Flaws & Architectural Corrections

### Flaw #1 & #3: CLI Logic & Replay Boundaries
**Risk:** `CLI = Game Logic`, and state mutates directly without the Ledger.
**Resolution:** The Command Pattern will be strictly limited to **Payload Dispatch**. Commands will parse user input into `CommandPayloads`. These payloads are passed to a `SimulationBus`. The bus validates the command, executes the game logic, and generates a `LedgerEvent`. The `LedgerEvent` is then applied to the Engines (State). **The CLI has no direct access to engine mutation.**

### Flaw #2: Env God Object
**Risk:** The `Env` struct holding all engines becomes a God Object.
**Resolution:** The `Env` will be replaced by an `ApplicationContext`. Commands will only require access to a `Dispatcher` (to send payloads) and `Views` (read-only projections of the current state). Commands never see the Engines.

### Flaw #4: Time.Sleep() vs Simulation Clock
**Risk:** Wall Clock vs. Simulation Clock mismatch.
**Resolution:** **Simulation Tick is Authoritative.** `time.Sleep` is strictly for UI pacing (aesthetic delay). Game logic relies entirely on the `Ledger Sequence` (logical time) and the `Simulation Tick` (game loop time). If the game pauses, the Substrate pauses.

### Flaw #5: Hardcoded Anomalies
**Risk:** Demo logic inside commands.
**Resolution:** Anomalies originate from an independent **Threat Generator Engine** that runs every Simulation Tick. The CLI only queries the `ObservationView` to display anomalies generated by the engine.

# WARDEN.EXE: Architectural Resolution & Audit 006

## I. Highest Priority Resolutions (Q581-Q606)

### Q581. Projection Recovery Model
Projections are ephemeral. Upon crash, the system restores the last valid Snapshot, then replays the canonical Ledger Event stream from that Snapshot to the current Ledger Head. Projections are never canonical.

### Q582. Authority Model
Capability-based. Authority is a token issued by the Court/Substrate to an Identity (linked to a Public Key). Capabilities have TTL (Time to Live) and specific scopes. Authority is revoked via the Ledger; any action attempted with an expired/revoked token is rejected by the Semantic Validator.

### Q591. RNG Authority Model
The Ledger stores the outcome of all non-deterministic events. Engines do not seed RNG; they consume recorded random values from the Ledger stream. This guarantees that replay on any architecture (x86, ARM) produces identical engine states.

### Q616. Event Versioning Strategy
Every event payload includes a `SchemaVersion`. The Validator treats events as immutable, and the Engine Projection layer includes migration functions to map old schema versions to current internal structures during replay.

### Q626. Snapshot Architecture
Checkpoints are generated every 1,000 blocks. A snapshot contains the full serialized State of all Engines and the Hash of the Ledger Head at that moment. Forensic recovery validates the Snapshot Hash against the Ledger Head before the projection layer is enabled.

### Q606. Constitutional Doctrine Rules
Doctrine forms a hierarchy. L4 Policies (e.g., economic settings) are lower priority than L3 Constitutional Rules (e.g., "The Warden must always protect system coherence"). Conflicts are resolved by the Court Engine using Counterfactual Simulation precedence.

# WARDEN.EXE: Architectural Resolution & Audit 007

## I. Highest Priority Resolutions

### Q601. Can any ECS component change without replaying an event?
**Resolution: NO.** This is a critical violation of our Event-Sourcing invariant. The `PopulationSystem` and all other systems must be refactored to:
1. `Update()` generates *Candidate Events* (e.g., `EventPopulationGrowth`).
2. `SimulationBus` validates/appends these events to the Ledger.
3. Engines project these events to update their state (`Apply`). 
Direct mutation of ECS components during the `Update()` loop is now prohibited.

### Q602. Canonical hashing strategy?
Canonical JSON serialization using ordered keys (e.g., `encoding/json` with manual struct ordering or a deterministic map-sorting wrapper) to generate a stable byte-representation before hashing. `json.Marshal` on maps is strictly forbidden for state hashing.

### Q611. Signature verification model?
The `AuthorityManager` must store Public Keys per `AuthorityRef`. Every event must include a `Signature` field. The `SemanticValidator` MUST verify the signature against the `Payload` before permitting the event to be appended to the ledger.

### Q619. RNG authority model?
**Option B (Ledger Authority) is mandated.** Omega Engine does NOT generate randomness. It requests a random outcome via an `EventRNGRequest` payload. The `SimulationBus` generates the random outcome, records it in the Ledger, and the projection engines consume the recorded value during the `Apply()` phase. This ensures perfect replayability.

### Q626. Resource scarcity model?
Constraints on population growth and institutional activity are mandatory. Resources (Food/Energy) are ECS components. An institution cannot trigger an `EventPopulationGrowth` unless the `ResourceProjection` shows sufficient capacity in its `PopulationSupport` variable.

### Q631. Tick execution contract?
A tick is a transactional boundary. All events generated in a tick are batched. The system performs: `Tick Start -> Generate Events -> Validate -> Append -> Atomic Projection Update -> Tick End`. Partial application is forbidden.
